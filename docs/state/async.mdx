Handles reach the DOM right away. Data from a server takes longer, so the page needs a plan for the wait.

Pass `computed()` an async function. Then wrap every read of it in `@try`. Add `@pending` for the wait and `@catch` for failure. With the router, the server sends the `@pending` content first. The data streams in after, on the same response.

Notice that the reader sees `Loading` before the data exists, and the swap needs no client fetch.

```tsrx Counter.tsrx
const details = computed(async ({ signal }) => {
	const q = name;
	return { title: await loadGreeting(q, signal) };
});

@try {
	<p>{details.title}</p>
} @pending {
	<p>Loading</p>
} @catch {
	<p>Could not load</p>
}
```

You read the settled value directly: `details.title`, not `details.value.title`. There is no `.loading` or `.error` field. The three blocks are the whole vocabulary.

`loadGreeting` is a plain function from a `.ts` file. The computed gets a `signal`, an `AbortSignal`. Pass it on so stale requests stop. When `name` changes, the computed runs again.

In the browser, `@pending` shows only if the wait passes 250 ms. Once it shows, it stays for at least 200 ms, so the page does not flicker.

:::warning[Read state before the first await]
Reads before the first `await` form the computed's inputs. A state read after `await` gives `MARKLESS_ASYNC_POST_AWAIT_READ`. Copy the value to a local first, as `const q = name` does above.
:::

:::danger[My async value renders nothing and the build fails]
Every markup read of an async value needs a boundary. A read outside `@try` gives `MARKLESS_ASYNC_BOUNDARY_REQUIRED`.
:::
